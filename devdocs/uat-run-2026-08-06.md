**QQ-1 — Resolved, no defect.** The board owner ran it by hand on 2026-08-06:
⌘K, type, Enter, and the palette closes as designed. `runCommand`'s
`setOpen(false)` was never in doubt; the reproduction below was an artifact of
synthetic key events, which is exactly why it was recorded as a question rather
than filed as a defect. The original note is kept below because the *reason* it
could not be settled by automation still holds for anything else that needs
trusted input.

**Was: does the palette close after running a command?**
`runCommand` calls `setOpen(false)` before `command.run()`, so it should. Driven
with synthetic key events it reproducibly did *not*: after Enter, both the
palette and the Edit dialog were open, the palette on top. But the trusted-input
path could not be driven either (the harness's Ctrl+K never opened it, and its
typing never reached the palette input), so this could equally be an artifact of
synthetic events. **Not recorded as a defect.** It is five seconds for a human:
press ⌘K, type a task name, press Enter, and see whether the palette goes away.

**OBS-4 — SUPERSEDED. Scripted drag-and-drop is reliable; the harness was
cutting the gesture in half.**

Suite 11 found the real cause. A drag driven from a *single* `javascript_tool`
call frequently dies partway: dnd-kit's drag-over work blocks the renderer long
enough that CDP's `Runtime.evaluate` hits its 45-second timeout, the script is
killed mid-sequence, and `pointerup` is never sent. The drag was starting every
time — the giveaway was a stranded drag-overlay card left in the DOM, a fourth
card the database knew nothing about.

**Split the gesture across separate tool calls** — `pointerdown` plus a few
activation nudges in one, the travel in a second, `pointerup` in a third, with
the target coordinates stashed on `window` beforehand — and it lands. UAT-055
dragged a task into a sprint and back out that way, both directions, persisted.
Stashing the target *before* the travel call matters: when that call does time
out, the following call can still finish the drop.

Backlog-lens drags landed consistently this way; board-lens drags across columns
still did not, which is why UAT-056's setup used a `PATCH`. The original text
follows.

**Was: scripted drag-and-drop is about half reliable.**
The board's only sensor is `PointerSensor` (5px activation) with no
`KeyboardSensor`, so there is no non-pointer path. `left_click_drag` picks the
card up and never drops it. A hand-written pointerdown → 15×pointermove →
pointerup on the card element does work, and is how UAT-018/019 passed — but it
failed about as often as it succeeded, usually resolving the drop onto the
dragged card itself. Retry and verify after a reload; never conclude a drag
failed from one attempt.

**OBS-3 — Synthetic clicks do not activate this app's controls (automation only).**
First recorded as a dnd-kit quirk on task cards; the menu sweep showed it is
broader and simpler than that. The harness's synthetic click focuses a control
but does not fire its handler — reproduced on task cards, **NEW TASK**, the `⋯`
trigger and the sidebar tools. A programmatic `element.click()` opens every one
of them first time, which proves the handlers are fine and the click is simply
not being delivered as activation (Base UI drives these from pointer events).

Not a defect, but it shapes how this app must be tested: **drive it with
`element.click()`, not synthetic pointer clicks**, or a swallowed click reads as
a broken feature. Two false defects were nearly filed before this was understood.

### ENV-2 — The compose stack serves `next dev` on a Windows bind mount, and it is slow

`docker-compose.override.yml` deliberately swaps the `app` service from the
production runner to `npx next dev --webpack` with the host source bind-mounted.
That is documented and intentional, and the override's own comments warn that
Docker dev on Windows is slow. The cost during this run:

- **first hit on any route: 3–24 seconds** (`POST /api/tasks` took 23.5s once);
- warm requests: ~0.27s.

This is not an app defect, but it is a UAT hazard. It caused two near-misses
where a create looked like it had silently failed, when in fact the write was
still in flight and the page text was read too early. Pre-warming every API
route with a burst of throwaway requests fixed the worst of it — compilation is
per-route and does not care whether the request was authorised.

**For the plan:** §1.4 should say to warm the app before testing, and that the
fast path for a UI run is local `npm run dev` rather than the compose stack.

## 3. Defects and observations

### UI-3 — Logged time is dated in the database's timezone, not the user's — **the run's first Fail**

Logging 30 minutes at **20:58 on 6 August, America/New_York**, produced an entry
dated **2026-08-07**. The browser agrees it is the 6th
(`Thu Aug 06 2026 20:58:27 GMT-0400`); the entry says tomorrow, and renders that
date to the user.

Root cause, `src/features/time/server/repository.ts:75`:

```sql
INSERT INTO time_entry (task_id, user_id, minutes, spent_on, note)
VALUES ($1, $2, $3, COALESCE($4::date, CURRENT_DATE), $5)
```

`CURRENT_DATE` is *the database server's* today, and the database runs UTC. The
client never fills the gap: `time-section.tsx` collects minutes and a note and
nothing else — there is no date field and `spentOn` is never sent — so the
`COALESCE` fallback is the only path a UI-logged entry can take.

**Who this bites and how hard.** Everyone behind UTC, for the last hours of every
day — from 20:00 Eastern, 17:00 Pacific. The entry is not merely displayed a day
late: `spent_on` is the column `timesheet.ts` groups by and filters between
(`WHERE ... te.spent_on BETWEEN $2 AND $3`), so an evening's work is reported on
the wrong day and, when that evening is a Sunday, in the wrong week. Anyone east
of UTC gets the mirror of it before 00:00 local.

**Why it survived until now:** `time.test.ts` only ever passes `spentOn`
explicitly (`{ minutes: 30, spentOn: "2026-07-18" }`), so the default branch —
the only branch the UI uses — has no test at all.

**Fixed — the owner chose the client-side date.** `TimeSection` now calls
`useToday()` and passes it as `spentOn`; `addTimeEntry` takes it as an optional
fourth argument and omits the key when it is absent, so the server's
`CURRENT_DATE` remains the fallback for a caller with no reader to ask — right
there, wrong only when a reader exists. This is the app's existing practice
rather than a new idea: `useToday` is how every other "today" here is decided,
and `localToday`'s own comment already names this bug class — building a date
from `toISOString` "would hand back tomorrow's date to anyone east of Greenwich
in the evening".

Pinned by a component test that fails against the old code for the right reason
(the POST body simply had no `spentOn`) and asserts the browser's local date
rather than a hard-coded string, so it states the rule instead of one zone's
answer.

**Re-run against the rebuilt app, and it now passes.** The bad entry was deleted
and 30 minutes logged again through the UI at **21:14 local on 6 August**, while
UTC had already turned over to the 7th. Stored as **`2026-08-06`**.

*A workspace timezone remains the larger answer* for a team spread across zones —
this fix makes each reader's own date authoritative, which is right for one
reader per entry and still leaves "which day is this for the team?" unanswered.
Not needed now; worth knowing where the seam is.

### UI-5 — Every milestone lands in "Unfiled" on the Roadmap, whatever epic it is filed under

The Roadmap's organising idea is that each epic is a swimlane —
`roadmap-view.tsx` says so in its own first line, and `buildRoadmap` groups
milestones by `epicId`. It cannot ever work: **the board payload does not carry
`epicId`.**

`src/features/board/server/repository.ts:73` hand-writes its own milestone
SELECT:

```sql
SELECT m.id, m.board_id AS "boardId", m.name,
       m.due_date AS "dueDate", m.created_at AS "createdAt", …
```

while `src/features/milestones/server/repository.ts:26` has a shared
`MILESTONE_COLUMNS` that includes `m.epic_id AS "epicId"` and
`m.objective_id AS "objectiveId"`. The board's copy omits both. The comment above
it explains the hand-writing — "listMilestones' own check would be a second
identical query — read the table directly" — a fair optimisation that quietly
dropped two columns. It is typed `query<Milestone>`, and TypeScript cannot check
a SQL result's shape, so nothing complained.

**Demonstrated end to end, not inferred:**

1. `UAT-MS-01` was filed under `UAT-Epic-01` — `PATCH /api/milestones/835`
   returned `200` with `"epicId": 750`, so the row is right in the database.
2. `GET /api/board/11332` returns that milestone with keys
   `id, boardId, name, dueDate, createdAt, total, done` — **no `epicId`**.
3. The Roadmap renders it under **Unfiled**, before *and* after the epic was set,
   across a reload.

So the swimlane is unreachable through any route: the lane a milestone belongs to
is decided from a field the lens is never sent. `objectiveId` is dropped by the
same line and will bite whatever reads it next.

The fix is to add the two columns to that SELECT — or better, to use the
`MILESTONE_COLUMNS` the other repository already maintains, so the two copies
cannot drift again. A regression test should assert the *shape* the board payload
returns, since the type annotation demonstrably does not.

### UI-6 — A milestone's epic and objective can only be set when it is created

**The server is ready and waiting.** `milestones/server/handlers.ts:93-114`

`PATCH` in UI-5's evidence above is that path working first time. Only the UI is
missing.

Worth weighing together with UI-5: fixing UI-5 alone makes epic lanes work for
milestones that happened to be created with an epic; fixing both makes the
Roadmap's structure something a user can actually steer.

### UI-1 — The first date-axis tick label is clipped on Timeline and Gantt

Both views render the axis tick at `left: 0%` with `-translate-x-1/2`, which
centres the label on its offset. Half of it then sits outside the track, and the
ancestor `overflow-x-auto` clips it: "Aug 5" renders as "g 5". Measured — the
label's box starts 14px left of the track's left edge. Every other tick is fine,
because only the first sits on the boundary; a tick landing on `100%` would clip
the same way on the right.

- `src/features/board/components/timeline-view.tsx:126`
- `src/features/board/components/gantt-view.tsx:249`

**Fixed.** The two lines were identical, so the rule went into one place —
`src/features/board/lib/axis-ticks.ts` — and both views call it: a tick on the
very start aligns its left edge, one within a label's width of the end aligns its
right edge, everything between stays centred. Padding the track was rejected: it
would misalign the labels from the bars, and bar/label agreement on one
percentage scale is the whole design. Interpolating the shift across the axis was
also rejected, though it needs no threshold — it drifts every label off the date
it marks, and a label that has moved is worse than one that is clipped, because
the clip is visible and the drift is not.

Verified in the running app: the first tick now reports `translateX(0px)` and
overhangs the track by **0px**, against 14px before; the other two still report
`translateX(-50%)`.

### ENV-1 — The app can only be signed into on the origin in `BETTER_AUTH_URL`

The first attempt at this run served the app with `npm run dev` on port 3111,
because 3000 was busy and the plan's port looked incidental. It is not. Two
attempts to sign in were refused:

```
ERROR [Better Auth]: Invalid origin: http://localhost:3111
POST /api/auth/sign-in/social 403
```

`auth.ts` trusts `http://localhost:3000`, `http://localhost:3789`,
`BETTER_AUTH_URL`, and anything in `BETTER_AUTH_TRUSTED_ORIGINS`. Adding 3111 to
that list would still not have been enough: `BETTER_AUTH_URL` also determines the
callback GitHub redirects to, and that URL is registered in the GitHub OAuth app.
So sign-in works **only** where the two agree.

On this machine that is the container, which sets
`BETTER_AUTH_URL=http://localhost:6810`. Port 3000 is claimed intermittently by
another project, and 3789 (also trusted) has no registered callback. The run
therefore moved to the container on 6810, rebuilt at the commit under test.

Worth adding to the plan's §1.4: *serve the app on the origin in
`BETTER_AUTH_URL` — any other port fails at sign-in with a 403, not a redirect,
and the error is only visible in the server log.*
